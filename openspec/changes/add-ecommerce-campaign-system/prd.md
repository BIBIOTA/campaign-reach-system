# PRD：電商行銷活動系統（活動模組 × 觸達）

## 1. Introduction

### Background

公司在推動行銷活動時，活動的優惠設定、對象圈選與訊息發送分散在不同工具與流程，且常需工程介入。這讓活動上線慢、行銷人員無法自助操作，也看不到觸達後的成效。本專案要為公司建立一套統一的行銷活動系統，讓行銷/營運人員能**自己設定活動、設定要發給誰、由系統可靠地把訊息送出去**，並能回頭檢視成效。

本期交付系統的後端能力（提供 API 供後台前端與其他內部系統介接），不含消費者前台與後台操作介面。

### 活動的兩個組成

MVP 的折扣/優惠券活動由兩部分組成，缺一不可：

- **優惠規則設定**：決定使用者可獲得「什麼優惠」（折扣類型、優惠內容、使用門檻與限制）。
- **觸達發送設定**：決定系統要把活動訊息「發給誰、何時發、如何追蹤」（對象、發送時機、通道與成效）。

兩者在系統中各自獨立設定、可分別演進，後續其他活動類型與通道皆沿用此結構。

### Problem Statement

行銷團隊缺乏一個統一、可自助、可追蹤的活動與觸達平台，導致：活動上線慢且仰賴工程、觸達分散難以管理、發送成效不可見、且難以隨活動類型與規模成長。

### Target Users

- **主要使用者：行銷／營運人員** — 設定活動內容、優惠規則、觸達對象與發送時機，並查看成效。
- **次要使用者：內部系統與團隊** — 電商主站（提供使用者行為以觸發活動）、後台前端團隊（呼叫本系統 API）。

## 2. Goals

- 讓行銷人員**自助上線折扣/優惠券活動**（首波），顯著縮短活動從設定到觸達的前置時間。
- 提供統一觸達能力：可**排程定時發送**，也可**依使用者行為即時觸發**（如棄購提醒）。
- 觸達結果**全程可追蹤**：每位收件人是否送達、活動整體送達率/失敗率一目了然。
- 能**穩定處理大量觸達**並隨規模成長：設計上可演進至單次百萬筆級，MVP 以壓測驗證 10 萬筆級流程可靠跑通。
- 以**活動帶來的轉換/營收**作為最終成功衡量，系統需提供可歸因的活動與觸達資料。

## 3. Non-Goals

- 點數/會員集點類活動（本期不做）。
- 消費者前台頁面與後台操作介面（本期僅提供後端能力）。
- 進階分眾／標籤引擎（先支援指定名單與簡單條件，如會員等級、地區）。
- Email 以外通道（簡訊、App 推播、LINE）的實際發送——本期僅在能力上預留，不交付。
- 滿額贈禮/加價購、限時特賣/閃購的完整功能——本期僅保留擴充能力，MVP 不交付。
- 百萬筆級的實測達標不在 MVP 驗收範圍（屬設計演進目標，MVP 以 10 萬筆級壓測驗收）。

## 4. User Stories

### US-001: 建立折扣/優惠券活動（優惠規則設定）
**Description:** 作為行銷人員，我要設定一個含折扣或優惠券規則的活動，以便對目標客群提供優惠。

**Acceptance Criteria:**
- [ ] 可設定活動名稱、起訖時間、優惠類型、優惠內容、使用門檻、使用限制、觸達對象與發送計畫。
- [ ] MVP 支援固定金額折抵、百分比折扣、優惠券代碼三種折扣/優惠券設定。
- [ ] 可設定是否需要滿額門檻，例如無門檻或滿指定金額可用。
- [ ] 可設定基本使用限制，例如每位使用者限用一次、活動總使用次數上限。
- [ ] 規則設定不完整或不合理時，系統明確告知錯誤並拒絕儲存，例如折扣為負、百分比超過 100%、結束時間早於開始時間。
- [ ] 活動建立後預設為「草稿」，需經確認才會排入發送。

### US-002: 管理活動生命週期
**Description:** 作為行銷人員，我要啟用、暫停、結束活動，以便掌控活動的有效期間。

**Acceptance Criteria:**
- [ ] 活動可在草稿→排程→進行中→暫停/結束之間切換，不合理的切換會被擋下並提示。
- [ ] 到達開始時間自動進入「進行中」，到達結束時間自動「結束」。
- [ ] 活動被暫停或結束時，尚未送出的觸達會被取消，不會誤發。

### US-003: 設定觸達發送（對象、時機、通道）
**Description:** 作為行銷人員，我要設定活動訊息要發給誰、何時發、用什麼通道，以便完成觸達發送設定。

**Acceptance Criteria:**
- [ ] 可指定觸達對象（指定名單，或以會員等級、地區等簡單條件圈選）。
- [ ] 可設定發送時機為「排程定時」或「使用者行為觸發」。
- [ ] MVP 以 Email 為發送通道，並在設定上預留未來其他通道。
- [ ] 觸達發送設定與優惠規則設定可分別儲存、分別修改。

### US-004: 排程定時觸達
**Description:** 作為行銷人員，我要讓活動在指定時間對一群對象發送，以便如期送出活動通知。

**Acceptance Criteria:**
- [ ] 到達設定時間時，系統自動對符合的對象啟動發送。
- [ ] 即使系統短暫異常或重啟，已到期但未處理的發送會被補上，不遺漏、也不重複發。

### US-005: 行為觸發觸達
**Description:** 作為行銷人員，我要讓活動依使用者行為即時觸發，以便支援棄購提醒等情境。

**Acceptance Criteria:**
- [ ] 使用者行為（如加入購物車未結帳）發生後，符合條件者會在合理時間內收到對應訊息。
- [ ] 排程與行為觸發兩種方式，發送結果與追蹤方式一致。

### US-006: 可靠送達與失敗處理
**Description:** 作為行銷人員，我要確信訊息會被可靠送出、失敗能被妥善處理，以便不漏發也不誤發。

**Acceptance Criteria:**
- [ ] 同一活動對同一人於同一發送週期不會重複發送。
- [ ] 暫時性失敗（如服務忙碌）系統會自動重試；確定無法送達（如地址無效、已退訂）不再重試並標記失敗。
- [ ] 多次重試仍失敗的會被獨立保留，供人工檢視與重新發送，不會靜默遺失。

### US-007: 查看觸達成效
**Description:** 作為行銷人員，我要查詢活動的觸達狀態與成效，以便評估活動效果。

**Acceptance Criteria:**
- [ ] 可查看單一活動的送達率、失敗率與各狀態人數分布。
- [ ] 可查詢特定收件人在某活動的觸達狀態（待發送/已送達/失敗等）。

### US-008: 大量觸達的可靠性驗證
**Description:** 作為系統維運者，我要驗證系統能可靠處理大量觸達，以便確認可支撐業務成長。

**Acceptance Criteria:**
- [ ] 以壓測資料驗證單次活動 10 萬筆級的對象展開與發送可完整、可靠地跑完。
- [ ] 大量發送期間，活動設定與其他活動的觸達不受影響、不被拖垮。
- [ ] 產出壓測報告（處理速率、各狀態分布、資源使用），作為演進至百萬筆級的基準。

## 5. Functional Requirements

### 優惠規則設定
- FR-001: 系統必須讓使用者建立、查詢、修改活動的優惠規則，包含名稱、起訖時間、優惠類型、優惠內容、使用門檻與使用限制。
- FR-002: 系統必須支援固定金額折抵、百分比折扣、優惠券代碼三種優惠類型（MVP）。
- FR-003: 系統必須支援設定是否需要滿額門檻（無門檻 / 滿指定金額）。
- FR-004: 系統必須支援基本使用限制（每位使用者限用次數、活動總使用次數上限）。
- FR-005: 系統必須在儲存時驗證優惠規則的完整與合理性（如折扣非負、百分比≤100%、結束時間不早於開始時間），不通過則拒絕並回報原因。
- FR-006: 活動建立後預設為「草稿」，需經確認才會排入發送。

### 觸達發送設定
- FR-007: 系統必須讓使用者設定觸達對象（指定名單，或以會員等級、地區等簡單條件圈選）。
- FR-008: 系統必須支援「排程定時」與「使用者行為觸發」兩種發送時機，且兩者追蹤方式一致。
- FR-009: 系統必須以 Email 作為首波通道，並在設定上預留其他通道日後擴充。
- FR-010: 優惠規則設定與觸達發送設定必須可分別儲存與修改。

### 活動執行與生命週期
- FR-011: 系統必須管理活動狀態（草稿/排程/進行中/暫停/結束），並只允許合理的狀態切換。
- FR-012: 系統必須依設定的起訖時間自動讓活動進入「進行中」與「結束」。
- FR-013: 系統必須將圈選對象展開為個別收件人，逐一發送並記錄每位收件人的發送狀態。
- FR-014: 系統必須避免同一活動對同一人於同一發送週期重複發送。
- FR-015: 系統必須在發送暫時性失敗時自動重試，確定失敗則標記、不再重試。
- FR-016: 系統必須將重試耗盡仍失敗的觸達獨立保留，供人工檢視與重新發送，不得遺失。
- FR-017: 系統必須在活動暫停或結束時，取消其尚未送出的觸達。

### 成效與範圍
- FR-018: 系統必須提供活動維度的成效彙總（送達率、失敗率、狀態分布）與單筆收件人狀態查詢。
- FR-019: MVP 必須完整交付折扣/優惠券活動的全流程；滿額贈禮/加價購、限時特賣/閃購僅保留擴充能力。

## 6. Non-Functional Requirements

- NFR-001（規模與擴充）：系統設計必須可演進至單次百萬筆級觸達，並能透過增加處理資源提升發送速率；MVP 驗收門檻為壓測驗證 10 萬筆級流程可靠跑通。
- NFR-002（不互相影響）：大量發送進行時，不得阻塞活動設定與其他活動的觸達。
- NFR-003（可靠送達）：訊息發送須具備自動重試與失敗保留機制，確保不靜默遺失；同時盡量降低重複發送。
- NFR-004（穩定性）：外部 Email 服務中斷時，系統須穩定降級並於恢復後續送，不造成連鎖故障。
- NFR-005（可觀測）：每位收件人與每個活動的觸達狀態須可查詢，以支撐成效評估與問題排查。

## 7. Technical Considerations

本節僅列產品面需知的依賴與邊界；完整技術架構、領域模型與實作細節見 `design.md`。

- 本期僅交付後端能力，透過 API 供後台前端與其他內部系統介接。
- 依賴電商主站提供使用者行為事件以支援「行為觸發」。
- 依賴外部 Email 服務商（如 SendGrid/SES）執行實際寄送。
- 架構採可水平擴充、非同步處理的設計以支撐大量觸達（細節見 `design.md`）。

## 8. Metrics

- **業務（最終成功）**：活動帶來的轉換率與營收，需可依活動歸因。
- **效率**：活動從設定到首次觸達的前置時間。
- **觸達品質**：送達率、失敗率、需人工處理的失敗比例。
- **規模驗證**：MVP 壓測達成 10 萬筆級全流程跑通並記錄處理速率，作為演進至百萬筆級的基準。

## 9. Open Questions

- 轉換/營收歸因所需的下游資料（如訂單成立）由哪個系統、以何種方式提供？
- 優惠券代碼是否需支援唯一序號（一人一碼）或共用代碼？影響使用限制的實作。
- 10 萬筆級壓測的「可接受完成時間」與資源上限為何（作為 MVP 驗收門檻）？
- 演進至百萬筆級時的目標完成時間與發送速率為何？
- 發送頻率政策（同人同活動最小間隔、跨活動每日上限）由誰、以什麼規則定義？
- Email 服務商選型，以及退訂/抑制名單的來源與更新方式。
